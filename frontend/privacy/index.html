1. About Kanakku & Core Features

Kanakku (referenced in source repositories as CashFlow / Kanakku) is a personal finance management web application designed to help individuals monitor, categorize, and understand their day-to-day spending and cash flow.

Core features include:

  • Multi-Channel Tracking: Logging and categorizing transactions across UPI, credit/debit cards, net banking, ATM cash withdrawals, and physical cash.
  • Local-First Architecture: Running on client-side storage where persistent financial records reside directly on the user's device in IndexedDB.
  • Automated Bank & UPI Alert Parsing: Optional, user-consented synchronization with Gmail to extract transaction records from bank and payment provider notification emails.
  • Financial Health Insights & Reports: Generating daily, monthly, and annual expense breakdowns, cash pool balances, and exportable PDF income statements.
  • Financial Assistant: Contextual personal finance chat powered by local deterministic ledger computations and Google Gemini AI.

3. Why Kanakku Requests Gmail Access

In modern digital payments (particularly UPI, debit cards, credit cards, and NEFT/IMPS transfers), banks and payment applications immediately transmit automated transaction receipt emails.

Without automated synchronization, users must manually type every single grocery purchase, ride-share fare, or utility payment. Kanakku's read-only Gmail integration automates this workflow:

  1. Kanakku executes targeted search queries against your Gmail mailbox to locate transactional confirmation emails.
  2. The system parses the date, amount, currency, merchant name, and payment method into a standardized transaction format.
  3. These transactions are returned to your browser to populate your local offline ledger.
Read-Only Safety Guarantee

Kanakku only asks for read-only access. The application cannot send emails from your account, modify your drafts, delete your messages, manage your labels, or alter your mailbox configuration.

4. Scope Limitations & Strict Email Exclusions

Kanakku employs rigorous API query filters and pre-filtering algorithms in code to ensure personal and non-transactional messages are completely bypassed:

  • Targeted Financial Queries: Searches are restricted to transactional keywords (such as "debited", "credited", "UPI transfer", "card payment", "ATM withdrawal", and "NEFT / IMPS transfer").
  • Strict Negative Exclusions: Searches explicitly exclude non-transactional emails at the Gmail API level, including:
    • Marketing campaigns, promotional offers, pre-approved loan advertisements.
    • Account statements and e-statement PDFs.
    • Login alerts, password reset notifications, and security notices.
    • One-time passwords (OTPs) and verification codes.
  • Candidate Pre-Filtering: If an email body or snippet contains words such as "otp", "one time password", or "verification code", it is immediately discarded and never parsed.
  • Personal Correspondence Ignored: Kanakku does not inspect or index personal messages, family or work emails, or social notifications.

5. How Google & Financial Data is Processed

Kanakku adheres to the architectural philosophy: Code Computes, Gemini Interprets.

  • Text Parsing Pipeline: Candidate financial notification emails are processed either via deterministic regular expression parsers or, when enabled, via the Google Gemini API.
  • Sanitization & Stripping: As soon as the structured financial fields (amount, date, merchant, payment mode, reference ID) are extracted, all raw email bodies (body, textBody, htmlBody, and combinedBody) are permanently deleted and stripped from memory before the data is transmitted to the client.
  • No Email Body Persistence: At no point are full email message bodies, email threads, or attachments written to persistent disk storage or database tables.

6. Data Storage Architecture: Local-First vs. Server Storage

To ensure maximum user privacy and protect sensitive financial lives, Kanakku maintains a strict division between client and server storage:

A. Client-Side On-Device Storage (IndexedDB via Dexie.js)

The following data lives strictly on your device in browser-isolated IndexedDB (cashflow_db_user_<userId>) and is NEVER saved to our server database:

  • All financial transaction records (amounts, dates, merchants, categories, payment types).
  • Monthly budgets, spending summaries, and financial health scores.
  • Locally generated financial statements and PDF exports.
  • Conversational chat history with the financial assistant.
  • Receipt scans and client-side OCR outputs.

B. Server-Side Database Storage (PostgreSQL on Neon / Local store)

The server database maintains only account identity, security, and sync state checkpoints:

  • users table: Account ID, email, display name, language preference, account status, and timestamps. (Passwords for email-only accounts are hashed with bcrypt; OAuth accounts store no password).
  • gmail_connections table: User ID, connected Google account email address, AES-256-GCM encrypted refresh token, AES-256-GCM encrypted access token, token expiry timestamp, and granted scope string.
  • gmail_processed_messages table: String Gmail message IDs and processing status (processed, skipped, or failed) to prevent re-fetching identical emails during subsequent syncs. (Never contains email text, subjects, or amounts).
  • gmail_sync_states table: Numerical synchronization telemetry (messages processed count, last sync timestamps, Gmail history ID checkpoint).

7. Security & Data Protection Measures

We implement concrete, verifiable technical protections based on actual source code implementation:

  • AES-256-GCM Token Encryption: All Google OAuth refresh tokens and access tokens stored in the database are encrypted at rest using AES-256 in Galois/Counter Mode (GCM) with random 128-bit initialization vectors (IVs) and 128-bit authentication tags.
  • Client Token Isolation: Google OAuth tokens are never sent to or stored in client-side browser storage (localStorage or IndexedDB). The client interacts with Kanakku only via signed, short-lived application JWTs.
  • HTTPS & Transport Security: All client-to-server and server-to-Google communication is encrypted in transit using Transport Layer Security (TLS/HTTPS).
  • CSRF Mitigation: OAuth authentication states use cryptographically randomized tokens verified with HMAC-SHA256 signatures stored in short-lived, HttpOnly, SameSite cookies.
  • Rate Limiting: Endpoints for authentication, Gmail synchronization, and AI interactions enforce strict rate limiting to prevent abuse and denial-of-service attempts.
Honest Security Transparency

We do not claim formal third-party compliance certifications (such as SOC-2, ISO 27001, or FedRAMP). We rely on transparent, open source, verifiable engineering practices and local-first architecture to safeguard your records.

8. Data Retention Policies

  • Local Ledger Records: Financial records stored in your browser's IndexedDB remain on your device until you choose to delete them, clear your browser's site data, or reset the application.
  • Server Account & Token Data: Server account records and encrypted OAuth tokens are retained only while your account remains active and connected.
  • Session Tokens: Application JWT access tokens expire after 2 hours; refresh tokens expire after 30 days unless renewed.
  • Sync Checkpoints: Processed message ID hashes are retained solely to deduplicate incoming messages across incremental sync intervals.

9. User Control, Data Deletion & Access Revocation

You have continuous, unconditional control over your data and Google account connections:

Method 1: In-App Gmail Disconnect

Inside Kanakku, navigate to Settings → Gmail Sync and click Disconnect Gmail. This instantly:

  • Permanently deletes the encrypted refresh and access tokens from our database.
  • Attempts an immediate token revocation call to Google's OAuth servers.
  • Resets all server-side synchronization states for your account.

Method 2: Google Account Permissions Revocation

You can revoke Kanakku's access directly through Google's management console at any time without opening the app:

  • Visit Google Account Permissions (myaccount.google.com/permissions).
  • Select Kanakku and click Remove Access.
  • When Kanakku detects revocation upon the next sync attempt (invalid_grant), the server automatically erases the stored connection record.

Method 3: In-App Local Ledger Deletion

Inside Kanakku, navigate to Settings → Account & Data and click Delete Local Ledger. This wipes all offline transactions, cash pools, conversation history, and financial statements stored in your browser's IndexedDB.

Method 4: Request Full Server Account & Data Deletion

To request the complete, irreversible deletion of your account record, email address, display name, and all associated sync metadata from our server database, send an email to:

10. Third-Party Sharing & AI Services

Kanakku does not sell, trade, license, or transfer your personal or financial data to outside commercial parties. We partner only with essential infrastructure service providers:

  • Hosting & CDN (Vercel): Delivers frontend static assets and executes serverless API handlers. Vercel acts as an infrastructure host and does not inspect application payload data.
  • Database Infrastructure (Neon / Cloud PostgreSQL): Hosts the relational server database containing account identity metadata and encrypted tokens.

Gemini processes the text under Google Cloud's data governance standards. Kanakku never passes OAuth credentials, API keys, or full email bodies to the AI service.

No Advertising or Profiling: Kanakku has no advertising integrations, third-party tracking pixels, or data brokerage arrangements.
